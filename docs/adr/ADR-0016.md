# ADR-0016: Kurtosis como piloto desechable, Docker Compose como red persistente

- **Fecha:** 2026-10-13
- **Estado:** Aceptado como estrategia; validación empírica pendiente.

## Contexto
Se necesita validar rápidamente Besu+Teku y siete validadores, pero el proyecto debe sobrevivir apagados completos entre clases, sin perder datos.

## Alternativas
Implementar génesis/Compose artesanal desde cero; usar Kurtosis también como solución permanente; usar Kurtosis sólo para pruebas y construir stack persistente después.

## Decisión
G0.1 empleará ethPandaOps ethereum-package en Kurtosis para probar EL/CL y finalidad. Se ancla el paquete a una revisión Git. La red definitiva deberá desplegarse por Docker Compose con datos en volumen por equipo, tras probar recuperación. Kurtosis no es el motor persistente definitivo, según limitación documentada de Besu/Teku en Docker.

## Consecuencias
El piloto no prueba directamente descubrimiento LAN ni persistencia entre días. Por lo tanto son checkpoints G0.2 y G0.3 independientes, con criterios propios. No declarar éxitos no ejecutados.

## Pruebas de aceptación
G0.1: ejecutar archivo de devnet/g0/kurtosis.yaml; probar height >0, 7 validadores active y finalized_epoch >0 con probe.py. G0.2: parejas separadas en LAN; G0.3: prueba 20/26/93/168 h con Docker Compose persistente.

## Reversibilidad
Cambios de requisito o plataformas deberán quedar en nuevo ADR que sustituya a éste. Las decisiones históricas originales en ADR-0002/0010 conservan su registro.
